## 0. 一页速览

**它到底是什么**：一个 AI 能力聚合网关，做三件互相咬合的事。

| 事      | 具体                       | 对应模块      |
| ------ | ------------------------ | --------- |
| **收敛** | 把 N 家上游收敛成一个 OpenAI 兼容端点 | 渠道 + 协议适配 |
| **计量** | 给调用方发密钥，按「模型单价 × 用量」扣额度  | 令牌 + 计费   |
| **留痕** | 每次调用记一条日志，供对账、排障、限流      | 日志 + 统计   |

一句话：**协议转换器 + 计量表 + 门禁**的组合体。它不生产模型，也不面向终端用户做界面。

**三条主链路**（任何改动都不能断）：

```
接入：渠道(Channel) → 模型(Model) → abilities(分组×模型×渠道) → 可被调度
计费：请求 → 预扣(PreConsume) → 上游 → 结算(Settle) → 写日志
鉴权：API Key(Token) → 用户(User) → 分组(Group) → 额度(Quota) → 渠道候选集
```

**规模基线**（实测）：后端 Go 非测试 115,509 行 / 94 个 controller / 242 个管理面 handler；前端 `web/src` 197,847 行 / 23 个 feature；渠道适配器 7 个；配置键 **140 个**。

## 1. 术语对照

官方叫法、运营叫法、数据库字段经常是三套词，这是「页面像面向开发者」的根源。

| 官方 / 代码         | 运营该叫     | 关键字段 / 位置          | 说明                       |
| --------------- | -------- | ------------------ | ------------------------ |
| 渠道 Channel      | **上游**   | `channels` 表       | 一个上游厂商账号（或一组 key）        |
| 分组 Group        | **谁能用**  | `group` 字段（逗号分隔）   | 渠道和用户都带分组，交集才可路由         |
| 令牌 Token        | **密钥**   | `tokens` 表         | 用户调用用的 `sk-...`          |
| 额度 Quota        | **余额**   | `users.quota`      | 整数，按 `QuotaPerUnit` 换算成钱 |
| 倍率 Ratio        | **单价系数** | `ModelRatio` 等     | 倍率制计价的乘数                 |
| 模型价格 ModelPrice | **固定单价** | `ModelPrice`       | 按次计价时用它，优先于倍率            |
| 分组倍率 GroupRatio | **分组折扣** | `GroupRatio`       | 在模型单价之上再乘一次              |
| abilities       | （不可见）    | `abilities` 表      | 分组×模型×渠道的可用性索引，**重启加载**  |
| 预扣 PreConsume   | 预估扣费     | `PreConsumedQuota` | 先扣一笔，结算时多退少补             |

## 4. 计费体系（最容易搞混的部分）

### 4.1 三种计价并存

| 模式          | 触发条件                        | 公式                                                                               | 典型场景        |
| ----------- | --------------------------- | -------------------------------------------------------------------------------- | ----------- |
| **倍率制**（默认） | 未设 `ModelPrice`             | `(prompt × ModelRatio + completion × ModelRatio × CompletionRatio) × GroupRatio` | 绝大多数文本模型    |
| **固定价**     | 设了 `ModelPrice`             | 每次调用扣固定额度                                                                        | 图片、按次计费模型   |
| **阶梯表达式**   | `BillingMode = tiered_expr` | 自定义表达式（按 token 区间/字段）                                                            | 复杂定价、长上下文阶梯 |

**优先级**：固定价 > 阶梯表达式 > 倍率制。三者同时存在时按前者算，这是最常见的「为什么扣的钱不对」的原因。

### 4.2 一次请求的结算时序

```
1. 鉴权：Key → 用户 → 分组 → 额度检查
2. 选渠道：分组交集中的渠道，按优先级/权重挑一个
3. 预扣：按估算 token × 单价扣一笔（PreConsumedQuota）
4. 转发：上游返回（流式则边收边算）
5. 结算：实际 token 重算，多退少补
6. 落日志：模型 / token / 额度 / 耗时 / 渠道 / 状态
```

**流式的中断**是最难的一段：客户端断开时按已产出 token 结算，未产出部分退回。这里是计费 bug 的高发区。

### 4.3 分组的三层含义

| 层  | 作用                          |
| -- | --------------------------- |
| 路由 | 用户分组 ∩ 渠道分组 ≠ ∅ 才有渠道可用      |
| 定价 | `GroupRatio` 在模型单价之上再乘一次    |
| 展示 | `UserUsableGroups` 决定前端能选哪些 |

**配错的典型症状**：`分组 X 下模型 Y 无可用渠道` ← 渠道建了但 `abilities` 没写，或分组不交集。

### 4.4 六个高频坑

1. 改 `QuotaPerUnit` → 历史金额显示口径全变
2. 只配 `ModelRatio` 不配 `CompletionRatio` → 输出按输入价算
3. 配了 `ModelPrice` 又配倍率 → 固定价优先，倍率白配
4. 缓存模型不配 `CacheRatio` → 缓存命中仍按全价扣
5. 自动下线阈值太小 → 渠道抖动反复上下线
6. `SelfUseModeEnabled` 打开 → 没配倍率的模型也能被调，且按 **37.5 的默认倍率**兜底结算（`GetModelRatioOrPrice` 的兜底值），很容易出现「我没定过这个模型的价格，怎么扣了这么多」

## 5. 渠道与调度

### 5.1 一条渠道的完整能力

| 字段                    | 作用                 | 谁在用      |
| --------------------- | ------------------ | -------- |
| `base_url` + `key`    | 接入信息               | 必填       |
| `models`              | 该渠道支持的模型清单         | 必填       |
| `group`               | 谁能用                | 必填       |
| `model_mapping`       | 客户端模型名 → 上游模型名     | 上游命名不一致时 |
| `param_override`      | 覆盖请求参数             | 上游参数不兼容时 |
| `header_override`     | 覆盖请求头              | 上游要求特殊头  |
| `status_code_mapping` | 上游错误码 → 标准错误码      | 客户端兼容    |
| `priority` / `weight` | 调度顺位与权重            | 多渠道同模型   |
| `auto_ban` + 阈值       | 连续失败自动下线           | 稳定性      |
| `channel_info`        | 多 key、轮询状态         | 单渠道多账号   |
| `setting`             | 渠道级额外设置（Azure 版本等） | 少量上游     |

### 5.2 调度规则

```
候选集 = 分组交集 ∩ 模型匹配 ∩ 状态启用
排序  = priority 降序 → weight 加权随机
失败  = 按 RetryTimes 换渠道重试
下线  = 连续失败达阈值 → 标记不可用 → 定时探测恢复
```

**这是中转站真正的技术核心**：同一个模型挂 3 家上游时，选谁直接决定可用性和成本。

| **P1 运营** | 日常要用    | 模型发现、价格同步、用户管理、分组、注册登录、审计、系统任务、限流                               |
| **P2 可选** | 特定场景才要  | 多 Key、渠道亲和、性能指标、余额告警、OAuth 多provider、阶梯计费                |
| **P3 冗余** | 与定位无关   | 订阅套餐、4 家支付中的 3 家、签到、Uptime Kuma、自更新检查、排行榜、多节点监控、Worker 代理、演示站模式 |



> P3 合计约 19,000 行前端 + 9,500 行 Go，已在精简方案 B1-B6 中分批处理。



## 8. 结合你的方向

**现状判断**（来自本轮盘点）：

| 维度   | 现状                |
| ---- | ----------------- |
| 上游成本 | 基本免费 → 不需要成本账/毛利账 |
| 对外形态 | 有真实注册用户，对外提供服务    |
| 运营人力 | 一个人               |
| 日常动作 | 看上游 + 配模型价格       |
| 主要痛点 | 页面多、术语像开发者、注意力分散  |

**定位建议**：更接近**场景 C（免费/低价分发）+ 少量场景 B 的计费能力**。这意味着：

1. 计费系统应从「财务系统」降级为「**配额系统**」——只需知道谁用了多少、还能用多少
2. 重心从「删功能」转向「**分配公平 + 异常处置 + 用户自助**」
3. 页面目标：一级 3 页（今日 / 上游 / 模型），其余下沉

**日常闭环**（一天的真实操作）：

```
看「今日」有没有待办 → 处理离线上游 → 给新模型定价 → 看有没有人异常消耗
```

四步之内应该全部完成，且不离开一个一级入口。
